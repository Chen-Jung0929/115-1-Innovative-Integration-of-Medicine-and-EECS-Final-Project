# Iteration 17：3D 骨架角度試驗（2026-11-22）

> 分支 `feature/world-3d-angles`（base：`feature/ui-redesign`）。試驗功能，2D 影像角度仍是主要量測與匯出值。

## 為什麼

使用者回饋：正面或斜角拍攝時，膝、髖角度常常「不太準」，例如深蹲蹲很低時左膝只顯示 21°、右膝 76°。原因是目前的角度都在 **2D 影像平面** 上算：正面拍時大腿朝向鏡頭，在畫面上被壓短，彎曲角就被低估；身體稍微轉一點，左右兩邊就差很多。

MediaPipe 除了 2D 點，也會輸出一組 **3D 骨架點（world landmarks，公尺、以髖為中心）**，之前沒有用到。

## 改了什麼

- `src/pose/mediapipe.ts`：每個點多存一個選填的 `world: [x, y, z]`（`Landmark.world`）。舊的分析檔沒有這個欄位，畫面會顯示 N/A，請重新分析。
- `src/biomechanics/world.ts`：`worldFlexion()` 用 3D 點算膝（髖–膝–踝）與髖（肩–髖–膝）的彎曲角 = 180° − 3D 夾角（`world-landmark-3d-flexion-v1`，自訂）。
- 畫面：膝、髖彎曲的大數字下面多一行小字「3D 骨架 X°」，只有該格 2D 角度通過 QC 時才顯示；「怎麼算？」裡有說明。
- 曲線：「曲線指標」多兩個選項「膝彎曲（3D 骨架，試驗）」「髖彎曲（3D 骨架，試驗）」。
- CSV、門檻、提示規則都沒有改；3D 點會跟著 landmarks 存在研究用 JSON 裡。

## 解讀與限制

1. **3D 骨架大幅降低對拍攝角度的依賴**：2D 只有接近正側面時準（最低點誤差 2–82°），3D 在每個角度都在約 3–19°。
2. **3D 站直時會顯示彎曲 8–29°**（模型的 3D 膝蓋幾乎不會完全打直），所以 3D 數字的變化範圍比實際小；先不做校正（用站直值扣除反而讓最低點變差）。
3. **3D 仍有 5–20° 誤差**，不能取代 OpenCap 雙鏡頭或動作捕捉；門檻不能直接用這個數字定。
4. 只有 2 位受試者、正確動作、實驗室光線。下一步：用研究組的資料（多鏡頭＋錯誤動作）重做，再決定主要數字要不要改用 3D 或「側面用 2D、其他用 3D」。

## 3D 骨架準確度改善：混合式 3D（2026-11-21，ADR-071～074）

### 問題

使用者說 3D 骨架「非常不準」。量測後原因有四個：
1. **站直也顯示彎曲 11–21°**：MediaPipe 的 3D 點（world landmarks）站直時把膝蓋放在髖–踝連線前方約 5 cm。
2. **骨盆不會往下、往後動**：3D 點以髖為中心，深蹲時看起來是腳往上縮，而不是人蹲下。
3. **沒有對齊重力、沒有地板**：骨架會斜、腳不在地上。
4. **畫面上的位置和影片對不起來**：3D 點自己的左右上下和 2D 關鍵點有出入（約 1.5–2% 身高）。

### 做法（全部是自訂方法）

`src/biomechanics/lift3d.ts`（純函式，有單元測試），`src/motion/world3d.ts`（整段影片接到畫面）：

1. **對齊相機**：每支影片求一個旋轉，把 3D 點轉成「相機看出去」的方向；每一格另外算尺度（像素／公尺），人走近鏡頭也不會變形。
2. **左右上下用 2D、前後用 3D**：2D 關鍵點在畫面內最準，所以骨架的左右、上下直接用 2D 點；只有「離鏡頭遠近」用 3D 點。骨架因此一定貼合影片。
3. **站直校正膝蓋深度**：找整段影片腿最伸直的 10% 取樣，當作站直，量出「膝蓋比髖–踝連線往前多少」，之後扣掉；蹲得越低扣得越少（蹲到底時不扣，因為全扣會讓最低點低估）。前提：影片中有站直的時候。
4. **腳踩地不滑**：著地的腳前後位置固定，反推骨盆往後移多少（深蹲時骨盆約後移 30 cm）。
5. **轉正、放上地板**：用 MediaPipe 3D 點本身的「上方」當重力方向；地板高度 = 每格最低腳點的中位數。
6. **平滑**：上傳影片前後各看 0.1 秒做平滑（不會延遲）；即時鏡頭版（`createCausalLifter`）只看過去，用 one-euro 濾波。

3D 膝、髖角（畫面小字與「曲線指標」的 3D 選項）改用這組點計算。2D 影像角度仍是主要數字，CSV、QC、門檻完全沒改。

### 驗證（DEV：OpenCap LabValidation subject2 squats1，5 支同步 iPhone）

- 跑的是 repo 裡的 TypeScript 程式（Python 只負責跑 MediaPipe Lite、存點位，和計算誤差）。
- 時間對齊用評審提供、以投影驗證過的固定影格差（不用角度互相關找最好的對齊，避免高估）。
- 「最低點」= 參考膝角前 15% 的取樣；「站直」= 後 15%。
- 髖的參考定義有兩種：(a) 關鍵點定義：用 OpenCap 三角量測的肩–髖–膝 3D 點算同一個角度（和我們的定義相同，只比 3D 準不準）；(b) `.mot` 的 hip_flexion − lumbar_extension（臨床定義）。注意：就算用 OpenCap 自己的 3D 關鍵點，(b) 也有 −18° 的系統差，這是定義不同，不是 3D 誤差。
- MPJPE（12 個點：肩、髖、膝、踝、腳跟、腳尖）：「整段」= 每支影片只做一次相似轉換；「髖中心」= 先扣掉骨盆位置；「逐格」= 每格各自對齊。單位 cm。
- 傾斜 = 對齊後我們的「上」和真實重力的夾角；地面 = 每格最低腳點高度和真值的差；重投影 = 骨架投影回畫面和 2D 關鍵點的距離（% 畫面身高）；抖動 = 相鄰三格的加速度（cm）。

App 實際用的是每秒 5 次（第一張表）；每秒 10 次供參考。

### 解讀

- **站直問題解決**：站直偏差由 11–21° 降到 1.5–7°（5 Hz 每個視角都在 ±5° 內，只有 75° 側面 7.3°）。
- **整段膝角誤差** 5 Hz 平均 11.8° → 8.5°；正面、45°、65° 達到 ≤ 8°，35° 斜角 9.2°、75° 側面 14.7° 未達標。
- **骨架位置**：整段 MPJPE 16.7 → 10.6 cm（5 Hz 平均），正面 6.7 cm；10 Hz 時 0–65° 都 ≤ 8.7 cm。
- **一定貼合影片**（重投影 0.3–0.7%），腳踩地板（誤差 3–8 cm），抖動比原始少 15–20%（10 Hz 少 65%）。
- **未解決**：
  1. 75° 側面在 5 Hz 時，MediaPipe Lite 在深蹲最低點把髖點放到腰上方（2D 點本身就錯），任何後處理都救不回來，最低點膝誤差 21°、髖 −50°。同一支影片每秒 10 次時最低點只差 4.8°：VIDEO 模式在低取樣率追蹤變差。若要改善需提高取樣率或改模型，待團隊決定。
  2. MediaPipe VIDEO 模式內建的平滑讓點位落後實際動作約 0–80 ms，快速深蹲時這會讓整段誤差多幾度；無法從單支影片估計，未補償。
  3. 髖角：以關鍵點定義，0–45° 偏差 −6 到 −13°；側面 −28 到 −50°（同上 2D 錯誤）。以臨床定義（.mot）偏差 −25° 以上，主要是定義差異；沒有用這位受試者的資料去「校正」定義，避免過度擬合。
  4. 只有一位 DEV 受試者、正確動作。

## 第二輪：評審稽核後的修正（2026-11-21，ADR-075～077）

評審用另一位受試者的資料（保留資料）和合成測試找出四個問題。**保留資料已經看過，這一輪只用 DEV 調整，並加上不需要真值的穩健性測試。**

### 1. 安全：站直校正不能把真的彎曲蓋掉（最重要）

舊做法假設「影片裡腿最直的時候就是站直」，如果病人膝蓋本來就伸不直（屈曲攣縮），或影片只拍到蹲下的片段，就會把真的彎曲當成誤差扣掉。

現在的做法（自訂）：
- 只有兩個**不靠深度**的檢查都通過才校正：
  1. 畫面上的腿長（髖到踝）至少是大腿＋小腿長的 95%（有扣掉鏡頭俯角的影響）；
  2. 影片上看到的膝彎曲 ≤ 25°。影片上看得到的彎曲一定是真的。這個門檻不設更低，是因為 MediaPipe 在側面站直時 2D 膝蓋就已經顯示約 20°。
- 就算校正，最多只改 10°。
- 每一側都會標示「已做站直校正（X°）」或「未校正（原因）」，顯示在 3D 骨架視窗下方。

新增的單元測試（合成資料）：
- 正面拍攝、膝蓋有 20° 屈曲攣縮但藏在深度裡，加上 5 cm 的模型偏差：3D 仍讀 ≥ 15°。
- 從頭到尾沒有站直（膝 > 45°）的片段：兩側都判定「未校正」，誤差不比原始 3D 大。
- 側面看得到的 30° 彎曲：不會被當成站直。

代價：正常人站直時，3D 膝角的偏差由 1.5–7° 回升到 6–11°。我們選擇寧可多顯示一點彎曲，也不要把真的問題蓋掉。

### 2. 重力（沒有達標）

評審指出：上一版的「轉正」其實就是 MediaPipe 3D 點自己的「上」，而它跟著手機轉。所以手機往下拍時，整副骨架會一起往後倒（保留資料約 12–14°）。

我們用 DEV 影片做了「模擬手機俯角」：影像套用旋轉的投影轉換，3D 點也一起旋轉，結果和評審看到的一致。試過的方法：
- **腳底地面平面**（腳跟＋腳尖接觸點，自訂）：會跟著俯角變化，但 MediaPipe 的腳跟點在影片上比腳尖高約 9 cm，造成 6–14° 的固定偏差，沒有達到 ≤ 5°。因此不當預設，只留作選項。
- **已知俯角**（`cameraPitchDeg`，例如之後從手機姿態感測器取得）：俯角 0°、10°、20° 時傾斜都在 3.6–8°。這是唯一有效的方法，但需要外部資訊，目前畫面還沒有接上。
- 結論：單一手機、焦距未知、只用 MediaPipe 時，找不到可靠的重力線索。畫面已註明「手機若上下傾斜，整副骨架會跟著前後傾」，並建議拍攝時手機保持水平。

### 3. 防呆

3D 點全為 0、任何點不是數字的取樣會被略過；最後算出的骨架只要有一個值不是數字，該格就不顯示骨架、也不算 3D 角度（有單元測試）。

### 4. 走路、髖

- **走路**：這一輪沒有處理（人走向鏡頭時，前後步距會消失）。
- **髖**：定義不動。畫面文字改為「3D 髖角只是近似值」，因為兩位受試者的偏差方向相反（−14° 到 +25°）。

- 另做了參數網格（起點 10–90°、過渡寬度、逐格或整段、近側腿或兩腿、權重上限）：最好的一組五視角平均只比混合式 3D 好 0.05°。這組參數是在 DEV 上挑的，不能當作改善的證據。
- 結論：不上線，畫面上的 3D 數字維持混合式 3D（ADR-078）。這一輪沒有改程式碼，也就沒有新增單元測試；held-out 沒有動。

## 第四輪：手機感測器俯角、站直改用時間判斷、10 Hz 分析

使用者選了兩個方向：用手機的傾斜感測器得到鏡頭俯角，以及把影片分析從每秒 5 次改成 10 次。

**做了什麼**
- 即時鏡頭：新增按鈕「使用手機傾斜感測器（鏡頭俯角）」。iPhone 一定要按按鈕、而且網址要是 https 才拿得到權限。量測段內的讀值取中位數，存進研究 JSON 的 `cameraPitch`，畫面顯示「鏡頭俯角 X°（手機感測器）」。
